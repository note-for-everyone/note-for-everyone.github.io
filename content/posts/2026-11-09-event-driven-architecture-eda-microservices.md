# 마이크로서비스 시대의 핵심 전략: Event-Driven Architecture (EDA)로 유연하고 확장 가능한 시스템 구축하기

급변하는 비즈니스 환경 속에서 오늘날의 소프트웨어 시스템은 그 어느 때보다 높은 유연성, 확장성, 그리고 복원력을 요구받고 있습니다. 특히 마이크로서비스 아키텍처가 대세로 자리 잡으면서, 각 서비스 간의 효율적인 통신 방식은 시스템 전체의 성능과 안정성을 좌우하는 핵심 요소가 되었죠. 기존의 동기식 요청-응답 방식만으로는 이러한 요구사항을 충족하기 어려운 경우가 많아지고 있습니다.

이러한 고민을 안고 계신 개발자, 아키텍트, 혹은 분산 시스템에 관심 있는 모든 분들을 위해 '오늘의 노트'가 새로운 아키텍처 패러다임, **Event-Driven Architecture(EDA)**를 소개합니다. EDA는 서비스 간의 결합도를 낮추고 비동기적인 처리를 통해 시스템의 응답성을 높이며, 장애 발생 시에도 전체 시스템이 멈추지 않도록 돕는 강력한 설계 방식입니다. 지금부터 EDA가 무엇인지, 왜 중요한지, 그리고 어떻게 활용할 수 있는지 자세히 알아보겠습니다.

## Event-Driven Architecture(EDA)란 무엇인가요?

Event-Driven Architecture, 즉 이벤트 기반 아키텍처는 시스템 구성 요소들이 '이벤트'라는 메시지를 통해 서로 통신하는 방식을 의미합니다. 여기서 이벤트는 시스템 내에서 발생한 어떤 '사실'을 나타내는 불변의 기록입니다. 예를 들어, "주문이 접수되었다", "결제가 완료되었다", "사용자 정보가 업데이트되었다" 와 같은 것들이 이벤트가 될 수 있습니다.

EDA의 핵심은 다음과 같은 세 가지 주요 구성 요소로 이루어집니다.

1.  **이벤트 생산자(Event Producer):** 특정 이벤트가 발생하면 이벤트를 생성하여 브로커에게 발행(publish)하는 역할을 합니다. 생산자는 이 이벤트를 누가 소비할지에 대해 알 필요가 없습니다.
2.  **이벤트 브로커(Event Broker/Bus):** 생산자가 발행한 이벤트를 받아 저장하고, 해당 이벤트에 관심 있는 소비자에게 전달하는 중간 매개체입니다. Apache Kafka, RabbitMQ, AWS SQS/SNS 등이 대표적인 예시입니다.
3.  **이벤트 소비자(Event Consumer):** 브로커에 발행된 이벤트 중 자신이 관심 있는 이벤트를 구독(subscribe)하여 받아 처리하는 역할을 합니다. 소비자 또한 이벤트가 어디서 왔는지 알 필요가 없습니다.

이러한 구조 덕분에 이벤트 생산자와 소비자는 서로에 대해 거의 알지 못하는 '느슨하게 결합된(loosely coupled)' 상태를 유지할 수 있습니다. 이는 시스템의 유연성과 확장성을 극대화하는 중요한 기반이 됩니다.

### EDA와 전통적인 요청-응답(Request-Response) 아키텍처 비교

EDA의 장점을 더 명확히 이해하기 위해, 우리가 흔히 사용하는 동기식 요청-응답 아키텍처와 비교해보겠습니다.

| 특징         | Event-Driven Architecture (EDA)                                     | Request-Response Architecture (REST API 등)                         |
| :----------- | :------------------------------------------------------------------ | :------------------------------------------------------------------ |
| **통신 방식** | 비동기 (이벤트 발행 및 구독)                                        | 동기 (요청 후 응답 대기)                                            |
| **결합도**   | 매우 낮음 (생산자와 소비자가 서로 알 필요 없음)                    | 높음 (클라이언트가 서버의 존재와 응답을 직접적으로 인지해야 함)     |
| **확장성**   | 매우 높음 (각 서비스 독립적 확장 용이, 새로운 소비자 추가 용이)     | 중간 (서비스마다 독립적 확장 가능하나, 의존성 때문에 제약 발생)     |
| **복원력**   | 높음 (생산자와 소비자 간의 직접적인 의존성 없어 연쇄 장애 위험 낮음) | 중간 (하나의 서비스 장애가 연쇄적으로 다른 서비스에 영향 줄 수 있음) |
| **실시간성** | 우수함 (이벤트 발생 즉시 처리 가능)                                | 요청 처리 시간만큼 응답 지연 발생                                   |
| **복잡성**   | 초기 설계 및 디버깅 복잡도가 높을 수 있음                           | 직관적, 초기 설계 단순                                              |
| **주요 사용처** | 마이크로서비스, IoT, 데이터 스트리밍, 복잡한 워크플로우           | 웹 서비스, CRUD 기반 API, 간단한 트랜잭션 처리                      |

## EDA의 실전 팁 & 활용 가이드

EDA는 단순히 기술적인 선택을 넘어, 시스템을 설계하는 사고방식의 변화를 요구합니다. 다음은 EDA를 효과적으로 활용하기 위한 실전 팁입니다.

1.  **이벤트 설계 원칙:**
    *   **불변성(Immutability):** 이벤트는 한 번 발생하면 변경되지 않는 '사실'이어야 합니다.
    *   **간결성(Conciseness):** 이벤트는 발생한 사실의 핵심 정보만 담고 있어야 합니다. 필요한 모든 데이터를 이벤트 자체에 담기보다, 이벤트 발생 시점에 필요한 최소한의 정보(예: ID)만 포함하고, 상세 정보는 필요할 때 해당 서비스를 통해 조회하도록 설계하는 것이 좋습니다.
    *   **버전 관리(Versioning):** 이벤트 스키마가 변경될 경우를 대비하여 버전 관리가 필수적입니다. 이전 버전의 이벤트를 처리할 수 있도록 하위 호환성을 유지하거나, 명확한 버전 업그레이드 전략을 세워야 합니다.
    *   **이벤트 명명 규칙:** "명사 + 과거 동사" 형태로 명명하여 발생한 사실을 명확히 전달합니다. (예: `OrderPlaced`, `PaymentProcessed`)

2.  **적절한 이벤트 브로커 선택:**
    *   **Apache Kafka:** 높은 처리량과 영속성, 확장성이 필요한 경우에 적합합니다. 데이터 스트리밍, 로그 수집, 실시간 분석 등에 주로 사용됩니다.
    *   **RabbitMQ:** 복잡한 라우팅 규칙과 메시지 전달의 신뢰성이 중요한 경우에 적합합니다. 다양한 메시징 패턴을 지원합니다.
    *   **클라우드 서비스:** AWS SQS/SNS, Azure Service Bus, Google Cloud Pub/Sub 등은 클라우드 환경에서 메시징 인프라를 직접 구축하고 관리하는 부담을 덜어줍니다.

3.  **멱등성(Idempotency) 구현:**
    *   이벤트 기반 시스템에서는 네트워크 문제 등으로 인해 동일한 이벤트가 여러 번 전달될 수 있습니다. 소비자는 동일한 이벤트를 여러 번 받아도 한 번만 처리한 것과 같은 결과를 내도록 멱등성을 구현해야 합니다. (예: 데이터베이스에 레코드를 삽입하기 전에 이미 존재하는지 확인)

4.  **장애 처리 및 모니터링:**
    *   **Dead Letter Queue (DLQ):** 처리 실패한 이벤트를 별도의 큐로 보내어 나중에 수동으로 확인하거나 재처리할 수 있도록 합니다.
    *   **재시도(Retry) 메커니즘:** 일시적인 오류의 경우, 일정 시간 간격을 두고 이벤트를 재처리하도록 구현합니다.
    *   **모니터링:** 이벤트 브로커의 상태, 이벤트 처리량, 소비자 지연(consumer lag) 등을 지속적으로 모니터링하여 병목 현상이나 장애를 조기에 감지해야 합니다.

5.  **예시 시나리오: 온라인 쇼핑몰 주문 처리**
    *   **기존 방식 (요청-응답):** `주문 서비스`가 `재고 서비스`에 재고 차감을 요청하고, `결제 서비스`에 결제를 요청하며, `배송 서비스`에 배송 시작을 요청하는 등 여러 서비스를 동기적으로 호출합니다. 이 중 하나라도 실패하면 전체 주문 처리가 지연되거나 실패할 수 있습니다.
    *   **EDA 방식:**
        1.  `주문 서비스`는 주문이 접수되면 `OrderPlaced` 이벤트를 발행합니다.
        2.  `재고 서비스`는 `OrderPlaced` 이벤트를 구독하여 재고를 차감하고, `InventoryUpdated` 이벤트를 발행합니다.
        3.  `결제 서비스`는 `OrderPlaced` 이벤트를 구독하여 결제를 처리하고, `PaymentProcessed` 이벤트를 발행합니다.
        4.  `배송 서비스`는 `PaymentProcessed` 및 `InventoryUpdated` 이벤트를 구독하여 모든 조건이 충족되면 배송을 시작하고, `ShippingInitiated` 이벤트를 발행합니다.
        이러한 방식은 각 서비스가 독립적으로 동작하며, 한 서비스의 장애가 다른 서비스에 직접적인 영향을 주지 않아 시스템 전체의 안정성이 높아집니다.
